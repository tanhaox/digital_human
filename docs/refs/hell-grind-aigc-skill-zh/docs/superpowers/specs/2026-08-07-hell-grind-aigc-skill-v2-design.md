# Hell Grind AIGC Skill v2 设计规格

- 日期：2026-08-07
- 状态：待用户复核
- 目标版本：v2.0.0
- 公开 Skill 名称：`hell-grind-aigc-skill`
- 中文名：AIGC 视频生产管理器
- 设计边界：完全独立运行，不依赖本机 8G 研究归档

## 1. 背景与问题

v1 已经完成一个可安装、模型无关、安全的父 Skill，并把生产管理和图片/视频提示词创作收进同一个入口。但它目前更像“项目骨架加提示词清单”，还没有把大规模公开项目研究中观察到的生产规律转化为足够细、足够可执行、足够可验证的方法。

当前主要缺口：

1. 提示词结构只列出图片 11 类信息和视频 12 段契约，缺少每类信息的写法、适用条件、冲突处理和失败修复。
2. 生产流程只有十阶段和少量退出条件，没有把资产状态、引用范围、空间关系、镜头首尾、声音、迭代和选片变成项目数据。
3. 现有校验器只检查基础表头、重复 ID 和少量引用，无法发现提示词内部冲突、镜头时长超载、选择记录悬空或连续性缺口。
4. 没有将大量重复生成体现出的“试错、选择和停止条件”沉淀为操作方法。
5. 缺少按失败现象进入的诊断路径。用户知道结果“不对”，却不知道应该改资产、镜头契约、提示词还是平台适配层。
6. 知识文档数量少且分工粗，Skill 很难只加载当前任务需要的内容。

v2 不以“增加文字量”为目标，而是把研究结果组织成一个独立的、可执行的 AIGC 视频生产操作系统。

## 2. 研究证据与设计推论

以下统计只用于支撑方法设计，不作为效果承诺：

| 观察 | 只读统计 | 设计推论 |
|---|---:|---|
| 生成记录总量 | 115,450 次 | 生成、评审、选择和返工必须是一等数据，不能只保存最终文件 |
| 非空提示词记录 | 115,313 条 | 提示词需要稳定版本、哈希和生成记录引用 |
| 去重提示词 | 7,482 条 | 不能把生成次数误认为创作方案数量 |
| 单提示词生成次数 | 中位数 11，平均 15.41，最高 439 | 建立候选批次、变量隔离、失败统计和停止条件 |
| 提示词长度 | 中位数约 6,380 字符，90 分位约 23,486 | 长提示词不是目标；需要分层、预算和冲突检查 |
| 空间调度模式命中 | 约 75.9% | 人物、机位、屏幕方向和前中后景必须成为镜头契约 |
| 镜头/焦段模式命中 | 约 76.8% | “电影感”必须拆成机位、焦段感、运动、对焦和结束构图 |
| 动作物理模式命中 | 约 75.5% | 动作要描述起因、接触、重量、反作用和停止状态 |
| 表演微动作模式命中 | 约 74.9% | 情绪必须翻译为视线、呼吸、停顿、面部和身体动作 |
| 声音底层模式命中 | 约 68.0% | 声音不是后补项；镜头阶段就要记录环境声、对白和关键音效 |
| 连续性模式命中 | 约 41.8% | 资产身份、状态和跨镜头接点需要独立单一数据源 |
| 负向约束模式命中 | 约 89.4% | 负面提示应针对已知失败，不能无上限堆叠 |
| 引用范围模式命中 | 约 21.0% | 每个参考必须说明继承什么、不继承什么 |

这些模式来自规则匹配，存在同义表达漏计或宽匹配；v2 将其视为方向性证据，不把比例包装成科学因果。

## 3. 目标

v2 必须实现：

1. 保持一个公开父 Skill，不拆出第二个可发现 Skill。
2. 同时覆盖项目搭建、项目审计、图片提示词从零生成与润色、视频提示词从零生成与润色。
3. 把方法论拆成按任务加载的参考模块，主 `SKILL.md` 只做路由和硬边界。
4. 建立模型无关的七层提示词架构和可检查的镜头契约。
5. 将资产、场次、镜头、提示词、生成、选片、连续性和交付连接成可追溯数据链。
6. 提供确定性、本地、零网络、零数据库的项目初始化、项目校验和提示词审计工具。
7. 让失败能被分类、定位到责任层，并生成最小修改建议。
8. 保持 v1 项目可继续校验；新增字段通过兼容迁移或可解释的 warning 引入。
9. 只发布原创方法、原创短例和通用模板，不重新分发研究项目的原始提示词、资产或视频。

## 4. 非目标

v2 不负责：

- 自动调用图片或视频生成模型。
- 自动扣费、上传、发布、部署或购买额度。
- 承诺某一模型一定遵循提示词。
- 为所有平台维护持续变化的私有参数表。
- 把长提示词当作质量分数的正向指标。
- 复制特定导演、艺术家、演员或现有 IP 的受保护表达。
- 代替人工进行最终画面、声音、剧情、权利和发布验收。
- 携带或下载 Hell Grind 的 8G 原始研究归档。

## 5. 总体架构

v2 采用“生产操作系统为主体，结构化契约为约束”的方案。

```text
用户请求
  ↓
单一父 Skill 路由
  ├── 生产搭建 / 管理 / 审计
  ├── 图片提示词：从零 / 润色
  ├── 视频提示词：从零 / 润色
  └── 失败诊断 / 质量检查
        ↓
按需加载知识模块
        ↓
七层提示词架构 + 项目单一数据源
        ↓
模板产物 / 提示词产物 / 审计报告
        ↓
确定性本地校验
```

设计原则：

- **渐进披露**：主入口保持短小，只有相关任务才读取相关参考。
- **事实分层**：项目事实、镜头意图、提示词文本、平台参数、生成结果和评审决定分开。
- **正向契约优先**：先说明要发生什么，再补少量针对性禁止项。
- **可见、可听、可计数、可计时**：把抽象意图改写成可验证结果。
- **变化最小化**：每次返工先定位失败层，只修改必要变量。
- **生成与发布分权**：写提示词和建项目永远不等于授权生成或发布。

## 6. Skill 入口与路由

### 6.1 主 `SKILL.md`

主文件控制在 500 行以内，目标约 120–180 行。它只包含：

1. 触发条件。
2. 请求分类方法。
3. 参考文件路由表。
4. 通用工作顺序。
5. 固定输出要求。
6. 本地工具调用入口。
7. 权利、费用、上传和发布边界。

frontmatter 的 `description` 以 `Use when...` 描述触发场景，不在描述中塞入完整工作流。

### 6.2 请求分类

每次调用确定以下维度：

| 维度 | 值 |
|---|---|
| 工作流 | 生产管理 / 提示词创作 / 审计诊断 |
| 媒介 | 图片 / 视频 / 混合项目 |
| 操作 | 从零生成 / 润色扩写 / 审核 / 搭建 / 迁移 |
| 丰富程度 | 精简版 / 标准版 / 导演版 |
| 项目上下文 | 独立提示词 / 已存在项目 |
| 提供方状态 | 未知 / 已知但不适配 / 明确要求适配 |
| 行为授权 | 仅文本 / 允许本地文件 / 明确生成 / 明确发布 |

### 6.3 加载规则

- 图片创作只加载共享架构、图片技巧、约束保护和质量评分。
- 视频创作按镜头类型加载共享架构、视频契约和一到三个专项技巧模块。
- 项目搭建加载生产流程、项目模式和质量门。
- 失败诊断加载失败分类，再根据责任层读取专项模块。
- 示例仅在用户需要示范或抽象规则难以理解时加载。
- 已有项目中的提示词必须先读取资产、场次、镜头和连续性事实。

## 7. 七层提示词架构

七层是图片和视频共用的内部思考框架，不要求每个最终提示词都显示七个标题。

### L1 创作意图与验收目标

回答：观众要看懂什么、感受什么、记住什么；这张图或这个镜头在项目中做什么。

规则：

- 一个镜头只保留一个主叙事功能。
- 把“高级、震撼、电影感”转换为可观察目标。
- 区分故事事实和视觉表现手段。

### L2 资产身份、状态与引用范围

回答：谁或什么出现；当前使用哪个批准版本；参考图只继承哪些属性。

规则：

- 身份锚点和当前状态分开。
- 角色、怪物、道具、场景和视效使用稳定 ID。
- 每个引用写明 `inherit` 与 `exclude`，例如只继承身份和服装，不继承原图构图、机位和光线。
- 参考图不能自动获得项目事实地位，必须登记并批准。

### L3 世界、空间与画面关系

回答：地点结构、前中后景、出入口、人物站位、屏幕方向、唯一道具和接触关系。

规则：

- 用可复现的空间锚点代替“在房间里”。
- 明确恰好人数和允许入镜对象。
- 左右同时记录解剖侧与屏幕侧，避免单写“左边”。
- 重要家具和道具声明唯一性、所有者和当前位置。

### L4 表演、动作与物理因果

回答：角色从什么状态开始，因为什么做什么，接触到什么，身体和环境怎样反馈，最后停在哪里。

规则：

- 情绪翻译为眼神、面部、呼吸、停顿、姿态和动作。
- 动作写成 `准备 → 发力 → 接触 → 反作用 → 落定`。
- 复杂动作必须拆节拍并服从时长。
- 禁止同时要求静止和大幅移动等互斥行为。

### L5 摄影机、构图、时间与剪辑

回答：从哪看、用什么景别和透视、怎样运动、什么时候切、最终画面停在哪里。

规则：

- 摄影机契约必须包含起始构图、主运动和结束构图。
- 一个镜头只有一个主运动；呼吸式微动属于稳定方式，不是第二主运动。
- 焦段写“视觉效果”优先，毫米数作为辅助。
- 多镜头必须明确切点、每段时长和动作接点。

### L6 光线、色彩、材质与声音

回答：光从哪里来、如何塑造体积；颜色怎样分工；表面如何响应光；镜头听到什么。

规则：

- 光源、方向、软硬、对比和曝光保护分开写。
- 60:30:10 是可选的颜色组织方法，不是所有镜头的固定咒语。
- 材质必须描述反射、粗糙度、透光、湿度、磨损等可见响应。
- 声音分为对白、动作拟音、环境底床、音乐和静默；未要求音乐时不得自动添加。

### L7 连续性、风险约束与交付规格

回答：哪些不能变、哪些只在本镜变化、最可能失败什么、最终交付要求是什么。

规则：

- 每个镜头使用三栏约束：`必须保持`、`本镜变化`、`禁止出现`。
- 负向约束来自已知风险或本轮失败，不复制无限通用负面词。
- 平台无关主提示词和平台适配层分离。
- 8K、IMAX 等词只能作为视觉目标或拍摄语汇，不能伪装成实际输出规格。

## 8. 提示词创作系统

### 8.1 四种模式

继续支持：

1. 图片从零生成。
2. 图片润色扩写。
3. 视频从零生成。
4. 视频润色扩写。

润色扩写必须先生成“约束快照”，至少包含：

- 原始意图。
- 不可改变的硬约束。
- 可增强区域。
- 明显冲突。
- 需要假设的缺失信息。

### 8.2 三种丰富程度

| 等级 | 使用场景 | 输出特点 |
|---|---|---|
| 精简版 | 快速探索、低复杂度单主体 | 只保留决定结果的核心字段，避免装饰性术语 |
| 标准版 | 常规生产与大多数单镜头 | 七层信息完整，但不重复资产事实 |
| 导演版 | 多角色、对白、复杂动作、多镜头或严格连续性 | 显式分段、时间轴、镜头首尾、声音、连续性和风险锁 |

丰富程度影响结构密度，不允许改变原始意图和硬约束。

### 8.3 图片 11 类信息

保留 v1 的 11 类结构，但每类扩展为四部分：

1. 字段目的。
2. 写作公式。
3. 常见失败。
4. 自写短例。

11 类为：主体数量、身份锚点、当前状态、动作姿态、场景空间、构图机位、镜头语言、光线曝光、色彩材质、风格媒介、技术与风险约束。

图片专项增加：

- 资产表与多视图设计。
- 同一角色不同状态的版本策略。
- 商品、道具和文字敏感画面的约束。
- 材质分区和光照响应。
- 参考图属性继承表。
- “身份一致”与“构图复刻”解耦。

### 8.4 视频 12 段镜头契约

保留 v1 的 12 段结构，但增加以下强制能力：

- `open_state`：首帧人物、道具、动作、机位和声音状态。
- `beat_timeline`：每个动作和对白的起止时间或相对节拍。
- `camera_start / camera_path / camera_end`。
- `close_state`：尾帧落点和下一镜接点。
- `continuity_in / continuity_out`。
- `must_hold / changes_here / must_not_appear`。
- `audio_cues`：时间、声源、空间位置和混音优先级。
- `risk_focus`：本镜最多三个优先风险。

### 8.5 镜头类型专项契约

为以下类型建立独立技巧章节，而不是套用一个通用长模板：

1. 单主体表演镜头。
2. 双人或多人对话镜头。
3. 复杂群像与人数锁定镜头。
4. 行走、追逐和跟拍镜头。
5. 打斗、撞击、投掷和爆炸镜头。
6. 怪物出场、变形与生物表演镜头。
7. 多镜头序列和蒙太奇。
8. 物件、环境和建立镜头。
9. 首尾帧或参考视频驱动镜头。
10. 无对白氛围和声音主导镜头。

每类说明：适用条件、必填信息、时长预算、常见冲突、失败症状和最小修复。

### 8.6 固定输出

提示词任务默认返回：

1. 模式与丰富程度。
2. 原始意图与硬约束快照。
3. 平台无关主提示词。
4. 平台适配层；提供方未知时明确留空。
5. 修改摘要；从零生成时改为设计摘要。
6. 假设与待确认项。
7. 质量评分。
8. 风险与首轮测试建议。

质量评分只用于发现缺口，不声称预测模型效果。

## 10. 生产管理系统

### 10.1 十阶段保持不变

目录继续使用 `00_brief` 到 `09_delivery`，保证 v1 心智模型和已有项目兼容。v2 在阶段内部增加结构，不增加无必要的第十一阶段。

### 10.2 单一数据源

| 事实 | 单一数据源 |

### 10.3 状态机

镜头状态：

```text
planned → contract_ready → prompt_ready → generated → reviewed → selected → locked
```

提示词状态：

```text

```

资产状态：


## 12. 提示词审计器

新增 `scripts/audit_prompt.py`，只读分析一个文本文件或标准输入。

### 12.1 接口

```bash
python3 scripts/audit_prompt.py prompt.md --medium video
python3 scripts/audit_prompt.py prompt.md --medium image --json
cat prompt.md | python3 scripts/audit_prompt.py - --medium video --json
```

### 12.2 检查范围

确定性检查，不调用语言模型：

- 缺失的核心模块。
- 人数、时长、左右、静止/移动等明显冲突。
- 多个主运镜冲突。
- 镜头时长与动作/对白节拍超载。
- 引用存在但缺少继承范围。
- 只有抽象形容词、缺少可见或可听行为。
- 首帧、尾帧或下一镜接点缺失。
- 负向约束数量过多、重复或互相冲突。
- 伪输出规格，例如把视觉目标误写成真实分辨率保证。
- 平台参数混入主提示词。
- 对话内容可能被错误视觉化但未声明音频边界。

### 12.3 输出

文本和 JSON 均包含：

- `valid_for_review`：是否达到人工评审条件，不代表生成一定成功。
- `score`：0–100 的结构完整度。
- `issues`：错误码、级别、证据行、说明和最小修复建议。
- `detected_modules`。
- `assumptions`。
- `network_requests: 0`。
- `database_operations: 0`。

审计器不得改写输入文件。

## 13. 项目校验器 v2

继续使用 `scripts/validate_project.py`，保持默认只读。

### 13.1 结构检查

- 必需阶段和文件。
- CSV 表头和必填值。
- ID 格式与唯一性。
- 状态枚举。
- 文件路径是否落在项目内。
- 版本号格式与父版本关系。

### 13.2 引用完整性

- 场次引用的地点资产存在且已批准。
- 镜头引用的场次、资产版本和提示词存在。
- beat 与 audio cue 引用现有镜头。
- 生成记录引用现有镜头和提示词版本。
- 选片引用现有生成记录。
- `selected_generation_id` 与选择日志一致。
- 连续性矩阵只引用现有镜头和资产。
- locked 镜头没有未处理 error 级连续性问题。

### 13.3 业务规则

- 每个镜头时长为正，场次内顺序不重复。
- beat 时间不越过镜头时长，且开始早于结束。
- 同一镜头不能同时选择多个主版本，除非明确记录合成用途。
- `selected` 或 `locked` 必须存在选片记录。
- `generated` 及以后状态必须存在生成记录。
- `prompt_ready` 及以后状态必须存在已检查提示词。
- 每次 iteration 必须声明改变变量，避免“全部重写”。
- 成本字段若存在必须为非负数；汇总只报告记录值，不推断缺失成本。
- 发布授权和生成授权分开。

### 13.4 兼容模式

- v1 项目缺少 v2 新文件时，默认给出 `warning` 和迁移建议，不立即判为无效。
- `--strict-v2` 将所有 v2 必需项提升为 error。
- 初始化的新项目直接采用 v2 模式。
- 不自动改写旧项目；以后可提供独立迁移计划，但不在本版本静默执行。

## 14. 失败诊断体系

每个失败码包含：症状、常见责任层、先检查什么、最小修复、复测变量和不建议做法。

### 14.1 资产与身份

| 错误码 | 症状 |
|---|---|
| `F-ID-DRIFT` | 脸、体型、发型或核心身份漂移 |
| `F-STATE-DRIFT` | 服装、伤势、湿度、污渍或携带物回退 |
| `F-REF-SCOPE` | 参考图的构图、光线或背景被错误继承 |
| `F-DUP-SUBJECT` | 同一角色重复或出现未允许人物 |
| `F-ASSET-MERGE` | 两个角色或道具特征融合 |

### 14.2 空间与连续性

| 错误码 | 症状 |
|---|---|
| `F-COUNT` | 人数错误 |
| `F-SCREEN-DIR` | 屏幕方向或解剖左右翻转 |
| `F-AXIS` | 越轴造成方向关系混乱 |
| `F-SPATIAL-RESET` | 场景布局被重构 |
| `F-PROP-DUP` | 家具或关键道具重复 |
| `F-CONTINUITY` | 动作、伤势、服装、天气或声音接不上 |

### 14.3 动作与表演

| 错误码 | 症状 |
|---|---|
| `F-ACTION-OVERLOAD` | 时长内动作过多，结果被压缩或遗漏 |
| `F-PHYSICS` | 漂浮、无重量、碰撞无反作用或轨迹错误 |
| `F-ACTION-ORDER` | 动作顺序错误 |
| `F-PERFORMANCE` | 表演僵硬、情绪过度或缺少反应 |
| `F-UNSCRIPTED-MOVE` | 被要求静止的角色自动做动作 |

### 14.4 摄影与剪辑

| 错误码 | 症状 |
|---|---|
| `F-CAMERA-CONFLICT` | 多个主运镜互相争夺 |
| `F-CAMERA-PATH` | 运镜起点、路径或落点错误 |
| `F-FRAMING` | 景别、主体占比或画面方向错误 |
| `F-FOCUS` | 对焦对象或景深错误 |
| `F-CUT` | 切点、镜头数量或转场错误 |
| `F-JITTER` | 故障抖动与有意手持混淆 |

### 14.5 对白与声音

| 错误码 | 症状 |
|---|---|
| `F-DIALOGUE-TEXT` | 台词不逐字、加词或漏词 |
| `F-DIALOGUE-TIME` | 台词超过时长或节拍不自然 |
| `F-DIALOGUE-VISUALIZED` | 台词提及内容被生成成闪回或额外人物 |
| `F-LIPSYNC` | 口型、说话者或静默角色错误 |
| `F-AUDIO-POLLUTION` | 自动音乐、旁白、字幕或无关人声 |
| `F-AUDIO-MIX` | 人声、环境声和音效优先级错误 |

### 14.6 光色与材质

| 错误码 | 症状 |
|---|---|
| `F-LIGHT-DIR` | 光源方向或阴影侧不一致 |
| `F-EXPOSURE` | 关键主体过曝或黑位压死 |
| `F-COLOR-DRIFT` | 主色和强调色关系漂移 |
| `F-MATERIAL` | 皮肤、金属、布料、骨骼等材质响应相同或塑料化 |
| `F-WEATHER` | 风雨雪雾未作用于人物和环境 |

### 14.7 诊断顺序

```text
先确认是否是资产事实错误
  ↓ 否
检查场景与镜头契约是否矛盾或超载
  ↓ 否
检查提示词是否遗漏、重复或含糊
  ↓ 否
检查平台适配参数与模型能力边界
  ↓
仅改变一个主要变量进行复测
```

不得默认通过“继续加长提示词”解决失败。

## 15. 迭代、批次和停止条件

### 15.1 批次原则

- 一个批次对应一个提示词版本和一组明确参数。
- 同一批次用于观察随机差异，不在批次内偷偷改提示词。
- 新版本必须记录改变变量和假设。
- 资产、动作、摄影机、声音和平台参数属于不同责任层，优先分开测试。

### 15.2 候选比较

候选不是只记“好/坏”，而是按镜头风险评分：

- 叙事功能是否成立。
- 身份与状态。
- 空间、人数和唯一物体。
- 表演与动作因果。
- 摄影机与构图。
- 光色材质。
- 对白与声音。
- 跨镜连续性。
- 技术缺陷。

### 15.3 停止条件

满足以下任一条件停止盲目增生：

1. 已有候选通过全部 hard gate 和项目设定的质量阈值。
2. 连续两个批次在同一错误上无改善，应回到责任层重写契约。
3. 达到批准的镜头预算或调用上限。
4. 失败来自已知模型能力边界，应降复杂度、拆镜头或换方案，而不是继续复制同一提示词。
5. 继续生成带来的预期收益低于剪辑、合成、补拍或人工修复成本。

## 16. 质量门

### 16.1 提示词门

- 硬约束可识别。
- 主体数量无冲突。
- 资产状态和引用范围明确。
- 动作、摄影机和对白服从时长。
- 首尾状态可检查。
- 负向约束针对当前风险。
- 平台参数与主提示词分离。

### 16.2 生成前门

- 镜头状态至少为 `prompt_ready`。
- 资产版本已批准。
- 生成次数、成本上限和提供方已获当前任务授权。
- 没有未解决的 error 级提示词审计问题。

### 16.3 选片门

- 选择理由和已知缺陷已记录。
- 关键连续性字段已比较。
- 不把“最漂亮”代替“最符合叙事和接点”。

### 16.4 交付门

- 技术规格、声音、字幕、权利和发布授权分别验收。
- 所有豁免有记录。
- 交付和发布是两个动作；`ready_for_delivery` 不等于 `published`。

## 17. 冲突优先级

当提示词内部发生冲突，按以下顺序处理：

1. 安全、法律、权利和平台明确限制。
2. 用户明确硬约束和逐字内容。
3. 项目已批准资产与连续性事实。
4. 镜头叙事目标和时长。
5. 动作、摄影机和声音契约。
6. 光色、材质与风格偏好。
7. 装饰性质量词和平台默认值。

不能静默牺牲高优先级约束来保留低优先级美学描述。必要时输出冲突和建议取舍。

## 18. 模型无关与平台适配层

### 18.1 主提示词

只包含创作和可观察结果：资产、空间、动作、摄影、光色、声音、连续性和交付意图。

### 18.2 平台适配层

只在用户给出提供方或明确要求适配时写入：

- 模型名称与版本。
- 时长、比例、分辨率等平台字段。
- 参考图角色与权重。
- seed、采样、强度、运动控制等私有参数。
- 已知能力限制和降级策略。

若提供方未知，输出 `provider: unspecified`，不得编造参数。

## 19. 性能、成本与安全约束

所有内置脚本：

- 网络请求：0。
- 数据库操作：0。
- 默认不读取项目目录以外的文件，显式输入除外。
- 不覆盖非空目标目录。
- 校验和审计保持只读。
- JSON 输出稳定，适合 CI。
- 中型项目的初始化与校验目标在普通本机数秒内完成。

Skill 本身：

- 不因提示词请求自动调用模型。
- 不因项目搭建请求自动下载媒体。
- 不因生成完成自动上传或发布。
- 费用、调用次数、提供方和生成授权必须在当前任务中明确。

## 21. 测试策略

开发遵循测试驱动：每项行为先写失败测试，再实现。

### 21.1 静态契约测试

- 仓库仍只有一个父 `SKILL.md`。
- frontmatter 可解析且 description 符合触发式写法。
- 路由表覆盖生产、图片、视频和失败诊断。
- 所有引用文件存在且可从主文件直接到达。
- 图片 11 类、视频 12 段和七层架构完整。
- 安全边界与固定输出存在。
- Skill 包内没有原始提示词语料或远程媒体。

### 21.2 初始化器测试

- 新项目生成完整 v2 模板。
- 用户参数正确写入。
- 非空目录拒绝覆盖。
- 初始化后严格 v2 校验通过。
- 网络与数据库计数为 0。

### 21.3 项目校验器测试

- v1 项目在兼容模式下只产生预期 warning。
- v2 项目严格模式通过。
- 错误表头、重复 ID、悬空引用、非法状态、越界 beat、错误选择、缺失连续性分别触发稳定错误码。
- 校验前后项目树哈希不变。
- 文本输出和 JSON 输出表达相同问题。

### 21.4 提示词审计器测试

- 完整图片和视频样例通过结构门。
- 缺主体、缺时长、缺首尾状态产生对应 issue。
- “完全静止”与“持续奔跑”等明显冲突被发现。
- 多个主运镜被发现。
- 动作或对白时间越界被发现。
- 重复负向约束被压缩建议命中。
- 审计器不修改输入。
- stdin、文件、文本和 JSON 模式一致。

### 21.5 行为测试

用场景化请求验证 Skill 是否正确加载和应用规则：

1. 用户发来简单图片需求时不输出过度冗长导演版。
2. 用户要求润色视频提示词时保留人数、时长和逐字台词。
3. 多角色动作镜头会主动建立空间、动作时间线和首尾状态。
4. 用户只要求写提示词时不会调用生成模型。
5. 用户要求诊断身份漂移时先查资产版本和引用范围，而不是只加负面词。
6. 用户要求“更电影感”时转换为摄影、光色和声音选择，而不是堆导演名。
7. 已有项目调用会引用批准 ID，不重新发明角色事实。
